# Distribution — plan

**Spec:** [10-distribution-spec.md](10-distribution-spec.md) · **Roadmap:** Phase 10

## Approach

Everything downstream of `git push origin v0.1.0` is generated: `dist` builds
four platform archives, writes the shell installer, and pushes a formula to
`robap/homebrew-tap`; a separate workflow reacts to the published release by
assembling the GHCR manifest from the two Linux binaries that release already
contains. **Nothing is uploaded by hand and nothing is compiled twice.**

Three things shape the order of the steps below:

- **Prove the risky parts before anything is public.** The musl build and
  `cargo package` are verified locally, and `dist plan` / `dist build` run on
  this machine, before a tag exists. A public release is close to one-way; a
  local `dist build` is free.
- **`v0.1.0-rc.N`, as many as it takes.** Prereleases do not publish to the tap
  (`publish-prereleases = false`), so an rc exercises the whole pipeline —
  including the GHCR workflow, since GitHub fires `release: published` for
  prereleases too — with nothing in front of a user. Only when an rc is green
  end to end does `v0.1.0` get cut, and every acceptance criterion is observed
  against that one.
- **CI lands first, before the release pipeline exists.** `.github/` does not
  exist today; a workflow that publishes binaries to the internet should not be
  the first thing in it.

Two design choices worth naming against their north stars. **Linux artifacts are
musl, not glibc** — north star 5, *single static binary*, which up to now has
been a property of the source tree and becomes a property of a downloaded file
here; it is also the only way the roadmap's older-distro criterion passes.
**The image keeps Phase 8's final stage byte for byte** and gains a build arg
that swaps where the binary comes from — the distroless base, the non-root uid,
`LANYARD_BIND=0.0.0.0`, and the `HEALTHCHECK` that runs `doctor --quiet` because
there is no shell are all already proven, and a second Dockerfile would drift
from them. Nothing in this phase adds a configuration knob (north star 1) or
touches the fixed port (north star 2).

## Files

- `.github/workflows/ci.yml` — **new.** fmt, clippy, test, `cargo package`, on
  `ubuntu-latest` and `macos-latest`. The file Phase 11 adds its example jobs to.
- `.github/workflows/release.yml` — **new, generated by `dist init`.** Never
  hand-edited; regenerated by `dist generate` whenever config changes.
- `.github/workflows/release-image.yml` — **new.** GHCR multi-arch build on
  `release: published`, plus `workflow_dispatch` with a tag input so a failed
  push is re-runnable without cutting a tag.
- `.github/workflows/release-smoke.yml` — **new.** `workflow_dispatch` with a
  tag input; the observer for the criteria that need macOS or arm64 hardware
  (spec criteria 6, 8, 9, and the arm64 half of 13). Durable, not throwaway —
  it is how the next release gets checked too.
- `dist-workspace.toml` — **new.** Targets, installers, tap, publish jobs,
  `github-custom-runners`.
- `Cargo.toml` — `[profile.dist]`; `.github` added to `exclude`.
- `CHANGELOG.md` — **new.** `dist` lifts the matching section into the release
  body.
- `Dockerfile` — `ARG BINARY_STAGE` selecting compile-here (today's default,
  unchanged) or copy-a-prebuilt-binary. Final stage untouched.
- `README.md` — `## Build and run` becomes `## Install`; a Windows paragraph;
  the container section moves to `ghcr.io/robap/lanyard`; the `cargo publish`
  sentence corrected.
- `ROADMAP.md` — Phase 10's platform list and the `brew services` claim.

## Risks & unknowns

- **`aarch64-unknown-linux-musl` linking.** Nothing in the tree needs a C
  toolchain — `reqwest` is `default-features = false` with no TLS, `rsa` and
  `sha2` are pure Rust — and Phase 8's Alpine stage already produces a musl
  binary, so this should be self-contained linking and nothing else. If it is
  not, `github-custom-runners` pinning arm64 to a native `ubuntu-24.04-arm`
  runner removes the cross-compile entirely. **Step 3 finds out before any
  workflow exists.**
- **`dist`'s Homebrew formula may be macOS-only.** Spec criterion 7 installs it
  in the `homebrew/brew` container, which needs `on_linux` URLs in the formula.
  If `dist` does not emit them, criterion 7 becomes the curl installer and the
  brew observation is macOS-only (criterion 8) — a spec amendment, not a
  blocker.
- **Intel macOS runners.** If `x86_64-apple-darwin` has no runner image
  available, it cross-compiles from an arm64 runner via `github-custom-runners`.
  Costs a config line; the artifact is the same.
- **A first GHCR push creates a *private* package.** Anonymous `podman pull`
  fails until it is made public in the package settings — a UI action, and step
  13 exists because it is invisible until criterion 12 fails.
- **`v0.1.0` is close to one-way.** Deleting a release after an installer has
  pointed at `/latest/download/` breaks anyone who ran it. This is why the rcs
  come first, and why the tap, the PAT and the public GHCR package are decided
  before the tag rather than during.
- **`cargo package` has never run here.** It could fail on something unforeseen
  in `tests/` or `web/dist/`. Step 2, early and cheap.
- **Spec criterion 10 needs a machine nobody in this repo has.** It is the
  operator's step, on their own Windows machine, and it is the last box.

- **CI caught a flaky test, and it was worth fixing rather than re-running.**
  `store::tests::a_recently_expired_entry_survives_a_sweep_so_it_can_say_expired`

  without a clock injection nobody else needs"). A test-only `expire()` helper
  backdates `expires_at` by a millisecond against a 60-second TTL, so the sweep
  must keep the entry for another sixty seconds — no scheduling delay can close
  that. Nothing in the shipped binary changed; the helper lives in the `#[cfg(test)]`
  module.
  Checked that the test was not merely made to pass: with the grace period
  removed from `sweep` (`expires_at > now`) it still fails, and it now runs in
  0.00s instead of 120ms. 10/10 clean under saturated CPU, where the old shape
  is the one CI found. The neighbouring
  `a_spent_id_is_eventually_forgotten_rather_than_remembered_for_ever` also
  sleeps, but in the safe direction — it needs the sleep to *exceed* a deadline,
  and overshooting only helps — so it was left alone.

- **`oci-mediatypes=false` and BuildKit's default attestations are mutually
  exclusive.** The dispatched image run failed on *both* architectures at the
  same step with `ERROR: cannot export attestations with "oci-mediatypes=false"`.
  BuildKit attaches a provenance attestation to every image by default, and an
  attestation can only be expressed in the newer OCI format — which is exactly
  the format we opted out of, because `HEALTHCHECK` is a field of the older
  Docker image config and this image's health probe is the only thing in it that
  can run.
  **Fixed with `--provenance=false --sbom=false`.** That is the resolution we
  wanted independently: each attestation is published as an extra entry with an
  `unknown/unknown` platform, which would clutter `podman manifest inspect`
  (spec criterion 13 reads that output) and would have made the `manifest` job's
  "expected 2 digests" check wrong.

- **`on: release: [published]` does not fire, and `v0.1.0-rc.1` is how we found
  out.** The rc's Release workflow went green and published the prerelease, and
  `release-image.yml` never started. The cause is a deliberate GitHub rule: the
  release is created by dist's `host` job using `secrets.GITHUB_TOKEN`, and
  GitHub does not start new workflow runs from events caused by that token —
  it is the guard against a workflow triggering itself forever. So the release
  event is simply never delivered.
  **Fixed by triggering on the Release workflow finishing instead**
  (`on: workflow_run: workflows: [Release]`), which does fire. The job is
  guarded on `conclusion == 'success'` and `event == 'push'`, the second because
  the Release workflow also runs on pull requests as a dry run. The tag comes
  from `workflow_run.head_branch`, falling back to whichever tag points at
  `head_sha` — and the step then checks that release really exists, so a wrong
  guess fails loudly instead of building an image from nothing.
  This is exactly what an rc is for: the failure cost nothing and nobody was
  pointed at it.

- **A release candidate needs the version bumped in `Cargo.toml` first.** `dist`
  refuses a tag that does not match a package version — pushing `v0.1.0-rc.1`
  with `Cargo.toml` at `0.1.0` fails the release workflow's first job with
  "This workspace doesn't have anything for dist to Release!". Verified locally
  with `dist plan --tag v0.1.0-rc.1`. So `Cargo.toml` (and `Cargo.lock`) say
  `0.1.0-rc.1` for the rc, and go back to `0.1.0` for the real tag.
  Two things that do *not* need changing: `CHANGELOG.md` keeps its single
  `## 0.1.0` section, because `dist` strips the prerelease suffix when it looks
  the section up (`announcement_changelog` is populated for the rc); and
  `tests/doctor.rs`'s `contains("lanyard 0.1.0")` still passes, because
  `lanyard 0.1.0-rc.1` contains that substring. Full suite green at the rc
  version: 555 passed.
