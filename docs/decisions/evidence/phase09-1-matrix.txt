==============================================================================
THE COUNTERFACTUAL — what SameSite=None; Secure would have done
==============================================================================

Run once on a throwaway patch to src/session.rs, reverted immediately. It is
here so the decision not to flip the cookie rests on a measurement rather than
on an assumption about how browsers treat http://localhost.

  set_cookie: lanyard_session=<id>; Path=/; HttpOnly; SameSite=None; Secure
  issuer:     http://127.0.0.1:9500/oidc   (the CROSS-SITE row)
  app:        http://localhost:5173/?renew=iframe

--- chrome
    Sec-Fetch-Site: cross-site
    Cookie: lanyard_session=5d77779ddfa243d58e4c29bb06b8f106
    <- 302 http://localhost:5173/silent-callback.html?code=dbc7a5448cc947e2baac4ddfa51348a2&state=2ecb9f04db234f3fa46ea7990ad447aa
    renewed: true

--- firefox
    Sec-Fetch-Site: cross-site
    Cookie: lanyard_session=85a3cb96782a43298599f964606a554f
    <- 302 http://localhost:5173/silent-callback.html?code=dac415529f8b4e35932126762c2afdae&state=69cf707ecaa343b0be97d6d4d9154800
    renewed: true

So: the browser DOES store and send a Secure cookie set over plain HTTP on
loopback, and the cross-site row renews. Flipping the cookie would "work".
It is still refused — north star 4, and Phase 0 obligation #1: a cookie that
claims Secure while lanyard serves http:// is one that silently stops being
sent the day the deployment changes, with nothing anywhere saying why.
src/session.rs::the_cookie_is_never_secure_and_never_expires is the guard,
and it still passes.
